# Функциональные требования Analytics Service

Дата актуализации: 23 ноября 2026 года.

Требования ниже фиксируют поведение текущей реализации. Формулировка «должен» означает зафиксированный контракт сервиса, а не обещание будущей функции. Документ составлен по коду; выполнение требований в запущенном окружении в рамках этой фиксации не проверялось. Архитектура описана [отдельно](analytics-architecture.md).

## Назначение

Сервис должен получать новые рабочие сообщения Telegram через RabbitMQ, извлекать из них изменения задач через OpenAI-совместимый LLM API, сохранять проверенные изменения и сообщать другим сервисам о новых задачах, блокерах и риске превышения оценки длительности.

Внешние участники: Ingestion Service — источник сообщений; RabbitMQ — транспорт; PostgreSQL — хранилище; OpenAI-совместимый LLM-сервер — анализатор; Dashboard Service — получатель аналитических событий.

## Приём сообщений

| ID | Требование и критерий приёмки |
| --- | --- |
| FR-01 | Сервис должен принимать `TelegramMessageCreated` через MassTransit/RabbitMQ и сохранять валидное событие в PostgreSQL до выполнения LLM-анализа. |
| FR-02 | Приём должен требовать непустой `EventId`, `SenderId > 0`, `MessageId > 0`, непустой текст длиной до 32 000 символов, непустые `CorrelationId` и `SourceInstance`, `Source = telegram`, а также `OccurredAt`, отличный от значения по умолчанию. Нарушение должно отклонять событие с ошибкой валидации. |
| FR-03 | При отсутствии непустой явной привязки в `Analytics:ChatTeams` сервис должен использовать строковый `ChatId` как идентификатор команды. Явная непустая привязка имеет приоритет. Отсутствие привязки не должно отклонять сообщение. Идентификатором сотрудника должен служить `SenderId`. |
| FR-04 | Повтор события с тем же `EventId` или сочетанием `(SourceInstance, ChatId, MessageId)` не должен создавать вторую запись inbox. Повторная доставка не должна заменять ранее сохранённый текст. |
| FR-05 | Сервис должен сохранять исходный payload, автора, текст, время события, время получения, корреляцию, источник, чат, команду, сотрудника и тред. Отсутствующий `ThreadId` должен сохраняться как `0`. |

## Формирование групп и контекста

| ID | Требование и критерий приёмки |
| --- | --- |
| FR-06 | Необработанные сообщения должны группироваться отдельно по команде, экземпляру источника, чату и треду. Сообщения разных групп не должны смешиваться в одном входе анализа. |
| FR-07 | Группа должна становиться доступной при паузе не меньше `IdleSeconds`, ожидании первого сообщения не меньше `MaxWaitSeconds` либо накоплении `MaxMessages` сообщений. Временные условия должны определяться по времени получения сообщений сервисом. |
| FR-08 | Одна группа должна содержать не более `MaxMessages` сообщений, выбранных по времени получения, затем `EventId`. Создание группы и назначение ей сообщений должны быть атомарными. |
| FR-09 | Работник должен выбирать доступные группы `ready` по времени создания, затем идентификатору, учитывая время следующей попытки. Сообщения в передаваемом модели входе должны сортироваться по времени события, затем `EventId`. |
| FR-10 | В контекст должны включаться задачи той же команды, принадлежащие авторам сообщений группы, включая завершённые. Если таких задач больше 20, группа должна переходить в `needs_review` без вызова модели. |
| FR-11 | Снимок входа анализа должен сохраняться до вызова модели и переиспользоваться при повторной обработке группы. Сохранённый результат модели должен переиспользоваться без нового инференса. |

## Извлечение изменений задач

| ID | Требование и критерий приёмки |
| --- | --- |
| FR-12 | Анализ должен выполняться отдельным HTTP-запросом к OpenAI-совместимому Chat Completions API с настраиваемыми endpoint, моделью и опциональным Bearer-ключом. Инструкции и снимок входа должны передаваться отдельными system/user-сообщениями. |
| FR-13 | Инструкция модели должна требовать JSON без Markdown, трактовать сообщения как недоверенные данные, запрещать выдумывание фактов и требовать пустой список изменений для обычного разговора. |
| FR-14 | Ответ должен иметь `schema_version = 1`, массив `changes` и массив `ambiguities`. Неизвестные JSON-поля, некорректный JSON, неподдерживаемая версия схемы и непустой список неоднозначностей должны приводить к `needs_review`. |
| FR-15 | Каждое изменение должно иметь уникальный в группе непустой `change_ref`, конечное значение `confidence` от `MinimumConfidence` до 1 включительно и хотя бы одно доказательство `evidence_event_ids`. Все доказательства должны принадлежать текущей группе. Невалидность любого изменения должна отклонять всю группу. |
| FR-16 | Сервис должен отправлять полный вход без автоматического усечения, с лимитом ответа `max_tokens`. Контекстные ограничения проверяет LLM-сервер; ошибка HTTP, в том числе из-за слишком большого контекста, должна обрабатываться повторными попытками группы. Локальный подсчёт токенов не выполняется. |
| FR-17 | HTTP-вызов и чтение ответа должны ограничиваться `TimeoutSeconds`, а генерация — `MaxTokens` через запрос. Ошибка HTTP или тайм-аут должны обрабатываться механизмом повторных попыток. Пустые choices/content и незавершённый `finish_reason` должны приводить к `needs_review`. JSON-режим должен включаться настройкой `UseJsonMode`. |

Допустимые действия:

| Действие | Результат и ограничения |
| --- | --- |
| `create_task` | Создать задачу с новым UUID, командой группы, исполнителем, заголовком и статусом `in_progress`. Требуются уникальный в группе `new_task_ref`, отсутствие `task_id` и исполнитель, являющийся автором хотя бы одного сообщения-доказательства этого действия. |
| `record_progress` | Записать непустое описание прогресса в историю; отдельное поле прогресса в состоянии задачи не создаётся. |
| `add_blocker` | Добавить блокер и перевести задачу в `blocked`. Завершённую задачу блокировать нельзя. Повтор блокера с тем же текстом без учёта регистра не должен создавать второй блокер или второе событие. |
| `resolve_blocker` | Удалить существующий блокер по точному тексту с учётом регистра. После снятия последнего блокера установить `in_progress`. Неизвестный блокер должен отклонять результат. |
| `set_next_step` | Сохранить непустой текст следующего шага. |
| `set_estimate` | Установить конечную оценку в календарных днях: `0 < estimate_days <= 3650`. |
| `set_status` | Установить `in_progress` или `done` при отсутствии открытых блокеров. При `done` сбросить признак риска. |

## Правила состояния и история

| ID | Требование и критерий приёмки |
| --- | --- |
| FR-18 | Для действий над задачей, кроме создания, должна быть указана ровно одна ссылка: `task_id` из контекста либо `new_task_ref` задачи, созданной ранее в этой группе. Неизвестная ссылка, действие или задача другой команды должны отклонять результат. |
| FR-19 | Заголовок, описание прогресса/блокера и текст следующего шага при использовании должны быть непустыми и иметь длину не больше 2000 символов. |
| FR-20 | Эффективным временем изменения должно быть максимальное `OccurredAt` его сообщений-доказательств. Для существующей задачи изменение с эффективным временем раньше `LastActivityAt` исходного снимка должно отклоняться. |
| FR-21 | Состояние задачи должно содержать идентификатор, команду, сотрудника, заголовок, статус, следующий шаг, оценку, время начала, последнюю активность, признак риска, версию и список открытых блокеров. |
| FR-22 | Для каждого принятого изменения должна сохраняться история с задачей, группой, `change_ref`, действием, payload, эффективным временем и временем записи. Версия каждой затронутой задачи должна увеличиваться один раз за применение группы. |
| FR-23 | Изменения задач, история, исходящие события и перевод группы в `applied` должны фиксироваться одной транзакцией. При конфликте версии существующей задачи транзакция должна откатываться, а группа — переходить в `needs_review`. Частичное применение группы недопустимо. |
| FR-24 | Валидный результат с пустым `changes` и пустым `ambiguities` должен завершать группу статусом `applied`, не создавая задач и аналитических событий. |

## Выявление риска

| ID | Требование и критерий приёмки |
| --- | --- |
| FR-25 | Сервис должен периодически рассчитывать риск в коде, независимо от вывода LLM. Риск установлен, если задача не завершена, имеет оценку и календарная длительность с `StartedAt` строго больше `EstimateDays × RiskMultiplier`. |
| FR-26 | При изменении признака риска сервис должен сохранить состояние, увеличить версию задачи и записать действие `set_risk` в историю. При переходе в риск должно создаваться событие `TaskAtRisk`; при снятии риска отдельное событие не требуется текущим контрактом. |
| FR-27 | Завершённая задача и задача без оценки не должны считаться рискованными. При множителе `1.5` и оценке 2 дня риск должен возникать после превышения 3 календарных дней с начала задачи, а не при равенстве этому порогу. |

## Публикация результатов

| ID | Требование и критерий приёмки |
| --- | --- |
| FR-28 | При создании задачи сервис должен формировать `NewTaskReported`, при добавлении нового блокера — `BlockerDetected`, при появлении риска — `TaskAtRisk`. Остальные действия должны сохраняться без отдельного интеграционного события. |
| FR-29 | Аналитическое событие должно содержать `EventId`, время события, `Source = analytics`, корреляцию, команду, задачу, заголовок, сотрудника, описание и массив доказательств. Для событий модели корреляция должна равняться идентификатору группы; для риска — идентификатору задачи, а массив доказательств должен быть пустым. |
| FR-30 | События должны сначала сохраняться в outbox в транзакции соответствующего изменения, затем публиковаться отдельным процессом через RabbitMQ. Отметка публикации должна выставляться только после успешного вызова публикации. |
| FR-31 | При повторной отправке outbox-события должен сохраняться его `EventId`; MassTransit `MessageId` должен равняться этому идентификатору. Контракт доставки допускает повторы и требует дедупликации от подписчиков, которым она необходима. |

## Ошибки, восстановление и настройки

| ID | Требование и критерий приёмки |
| --- | --- |
| FR-32 | Для невалидного или неоднозначного результата группа должна переходить в `needs_review`, для исчерпанного лимита попыток — в `failed`. Эти группы не должны автоматически выбираться как `ready`. |
| FR-33 | После временной ошибки доступность группы должна откладываться на `min(300, 2^attempt × 5)` секунд. Число попыток инференса должно сохраняться в БД; после достижения `MaxAttempts` новый инференс не должен запускаться. Уже сохранённый результат может быть применён без нового инференса. |
| FR-34 | После перезапуска сервис должен продолжать работу с сохранёнными входящими событиями, доступными группами `ready` и неопубликованными outbox-событиями. |
| FR-35 | Между экземплярами сервиса должна обеспечиваться единственность активного работника анализа и отдельно — единственность активного издателя outbox. Приём сообщений должен оставаться независимым от длительности инференса. |
| FR-36 | При запуске сервис должен создавать таблицы и индексы по модели EF Core для пустой БД и валидировать параметры анализа и модели. Существующая полная схема и JSONB-данные должны использоваться без удаления. Дополнение частичной схемы и миграции не входят в текущую автоматическую инициализацию. Подключения, привязки чатов, интервалы, лимиты, порог уверенности, множитель риска и параметры модели должны задаваться конфигурацией. |
| FR-37 | Сервис должен логировать применение групп, переход в ручную проверку и ошибки обработки/доставки. Подписки на редактирования Telegram и Git-события должны только логировать приём, без изменения задач. |

Значения по умолчанию: пауза — 60 секунд; максимальное ожидание — 300 секунд; размер группы — 100; период работника — 5 секунд; лимит попыток — 5; уверенность — 0.85; множитель риска — 1.5; ответ — до 1500 токенов; тайм-аут API — 300 секунд. Endpoint — `http://localhost:11434/v1/chat/completions`, модель — `qwen2.5:7b`, JSON-режим включён.

## Проверочные сценарии

1. Передать валидное событие без ручной привязки чата, дождаться готовности группы и получить корректный ответ модели с `create_task`. Ожидаются команда с ID чата, задача, история, группа `applied` и `NewTaskReported` в outbox.
2. Доставить одно входящее событие повторно. Ожидается одна запись inbox, без повторного включения сообщения в анализ.
3. Передать сообщения из двух непривязанных чатов. Ожидаются записи inbox с разными `TeamId`, равными ID соответствующих чатов; явное переопределение команды должно иметь приоритет.
4. Получить ответ модели с `ambiguities`, недостаточной уверенностью либо доказательством вне группы. Ожидается `needs_review`, без частичного изменения задач.
5. Создать задачу, добавить блокер и попытаться завершить её без снятия блокера в одной группе. Вся группа должна быть отклонена. При корректной последовательности со снятием блокера завершение допустимо.
6. Для незавершённой задачи с оценкой 2 дня и множителем 1.5 проверить момент ровно через 3 дня и момент после него. Ожидается отсутствие риска в первом случае и появление риска с событием во втором.
7. После сохранения входа/результата анализа перезапустить сервис. Ожидается продолжение обработки сохранённой группы; при наличии результата повторный инференс не требуется.
8. Прервать доставку outbox и восстановить RabbitMQ. Ожидается повторная попытка публикации; повторно доставленное событие должно сохранять исходный `EventId`.

Сценарии задают ожидаемые результаты проверки; они не являются отчётом о выполненных тестах.

## За пределами текущих требований

- Анализ редактирований и удалений Telegram, а также содержимого Git-событий.
- Автоматическое объединение разных чатов в одну команду и анализ без устойчивого `SenderId`.
- Полная история переписки, семантический поиск, RAG и автоматическое сокращение слишком большого контекста.
- Автоматическое разрешение неоднозначностей, интерфейс ручной проверки и API повторного запуска `needs_review`/`failed`.
- Публикация всех изменений задачи, дайджесты, пользовательский Dashboard и SignalR.
- Учёт рабочих дней, отпусков и индивидуальных календарей при расчёте риска.
- Гарантия доставки ровно один раз и параллельный анализ групп разными работниками.

Для расширения этих границ требуется отдельно согласовать новые требования; перечисленные функции не следует считать реализованными.

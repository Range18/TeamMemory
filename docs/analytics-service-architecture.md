# Analytics Service: архитектура, план разработки и критерии приёмки

Дата: 10 ноября 2026 года. Статус: предлагаемая спецификация для разработки.

## 1. Назначение и границы

Analytics преобразует события рабочих чатов и Git-репозиториев в задачи сотрудников, подтверждённый прогресс, блокеры, риски и историю изменений. Сообщения анализируются группами. Каждое применённое изменение должно быть связано с исходными данными.

Ingestion отвечает за Telegram/Git, проверку входящих webhook, нормализацию и публикацию событий. Analytics отвечает за приём, хранение контекста, анализ, состояние задач и данные для дайджеста. Digest/Dashboard отвечает за текст и расписание сводок, уведомления и интерфейс руководителя.

Начальный вариант: один развёртываемый Analytics Service с внутренними workers и небольшим HTTP API, PostgreSQL и RabbitMQ. Redis, векторная БД и отдельный микросервис для LLM на первом этапе не требуются. Вызовы LLM не выполняются внутри RabbitMQ consumer.

### Текущее состояние репозитория

Реализованы регистрации потребителей восьми конкретных контрактов, повторы через 1/5/15 секунд, JSON-логи и `ProcessedEventStore` в памяти. Обработчики только логируют получение. Есть локальные проверки дедупликации. PostgreSQL, накопление групп, анализатор, задачи, API и экспорт Prometheus ещё не реализованы. Сквозная проверка с RabbitMQ ранее не выполнялась из-за ограниченного доступа к Docker.

## 2. Поток обработки и компоненты

Последовательность:

1. `Event Consumer`: принять событие и сохранить в PostgreSQL inbox.
2. `Event Projector`: преобразовать сырое событие в сообщение, его ревизию либо Git-активность.
3. `Batch Builder`: накопить новые сообщения одного обсуждения и зафиксировать состав группы.
4. `Context Builder`: добавить ограниченный контекст обсуждения и текущие задачи.
5. `Analysis Worker`: вызвать LLM через адаптер с rate limiter и получить структурированный результат.
6. `Result Validator`: проверить формат, ссылки, доказательства и допустимость изменений.
7. `Task Change Applier`: одной транзакцией изменить задачи, записать историю и завершить применение группы.
8. `Staleness Worker`: независимо от поступления сообщений пересчитать риски по времени.
9. `Read API`: вернуть Digest актуальное состояние и изменения за период.

Это внутренние компоненты сервиса, не отдельные микросервисы. Состояние очереди работ и контекст находятся в PostgreSQL; память процесса используется только для временных объектов и оптимизаций.

### 2.1. Основной сценарий: обсуждение работы → состояние задач → данные дайджеста

Это целевой сценарий после реализации архитектуры, а не описание уже работающих возможностей текущего кода.

**Цель:** по группе сообщений сотрудника обновить прогресс, обнаружить блокер и предоставить Digest подтверждённую картину работы.

**Предусловия:** Ingestion публикует согласованные контракты; подписки Analytics созданы; PostgreSQL доступен; чат привязан к команде; стабильная идентичность автора связана с сотрудником. В Analytics уже существует задача Ивана «Интеграция API клиента» со статусом `in_progress`. Её оценка — два календарных дня, начало работы — четыре дня назад. Пример предполагает однозначную связь обсуждения с этой задачей.

**Триггер:** в одной ветке Telegram в течение 40 секунд появляются сообщения Ивана:

> «По интеграции API: авторизацию закончил».
>
> «Продолжить пока не могу — жду доступ к production API от клиента».
>
> «Как дадут доступ, проверю интеграцию целиком».

**Основной поток:**

1. **Ingestion публикует три события.** Для каждого сообщения передаёт стабильные идентификаторы, автора, чат/ветку, время источника, текст, EventId и CorrelationId. Analytics получает их через собственные очереди RabbitMQ.

2. **Consumer надёжно принимает каждое событие.** Проверяет контракт, команду и ключи дедупликации, сохраняет оригинальный payload в `inbox_events` со статусом `pending`. После commit подтверждается конкретная доставка RabbitMQ. На этом этапе LLM не вызывается и состояние задачи не меняется.

3. **Projector сохраняет сообщения.** Фоновый worker захватывает события, определяет сотрудника и ветку, записывает `messages`/`message_revisions`. Каждое событие становится `projected` в той же транзакции, что и его нормализованные данные.

4. **Batch Builder накапливает обсуждение.** Три сообщения попадают в одну `collecting`-группу команды и ветки. После 60 секунд без новых сообщений группа закрывается при ближайшей проверке накопителя: состав и ревизии фиксируются, состояние становится `ready`. Новые реплики после закрытия попадут в следующую группу. При непрерывном обсуждении сработает MaxWait или ограничение размера.

5. **Context Builder собирает ограниченный снимок.** Загружает три новых сообщения, необходимые предыдущие реплики ветки, данные Ивана и задачу «Интеграция API клиента» с её версией, статусом и открытыми блокерами. Задачи другой команды исключаются. Новые данные отделяются от справочных.

6. **Analysis Worker выполняет один запрос на группу.** После получения разрешения rate limiter фиксирует запрос и версии контекста, вызывает LLM без открытой транзакции БД и сохраняет ответ. В успешном сценарии без повторов три сообщения требуют одного обращения к модели.

7. **LLM предлагает структурированные изменения.** Ответ по JSON Schema содержит `record_progress` — «Реализована авторизация», `add_blocker` — «Ожидает доступ к production API от клиента», и `set_next_step` — «После получения доступа проверить интеграцию целиком». Каждая операция ссылается на существующую задачу и конкретные новые сообщения с их ревизиями. Завершение авторизации не трактуется как завершение всей интеграции.

8. **Validator проверяет предложение.** Проверяет схему, идентификаторы, команду, доказательства, уверенность и доменные правила. Перед применением подтверждается, что версия задачи и ревизии сообщений актуальны. В основном сценарии все проверки проходят, результат готов к применению.

9. **Task Change Applier сохраняет результат одной транзакцией.** Добавляет прогресс, создаёт открытый блокер, переводит задачу из `in_progress` в `blocked`, записывает следующий шаг, доказательства и историю с временами фактов и регистрации. Увеличивает ревизию команды и переводит группу в `applied`. Все изменения становятся видны вместе; повторное применение того же анализа исключено.

10. **Staleness Worker независимо проверяет сроки.** На очередном периодическом запуске видит четыре календарных дня при оценке два дня. По начальному правилу `4 > 2 × 1.5` выставляет `at_risk` и записывает изменение. Это отдельный процесс: он не требует нового сообщения или дополнительного LLM-вызова. Подтверждённая новая активность обновляет `last_meaningful_activity_at`; признак `stale` рассчитывается отдельно.

11. **Digest запрашивает согласованный срез.** По расписанию своего сервиса получает через внутренний API задачи и изменения за нужный период в часовом поясе команды. API возвращает задачу `blocked`, прогресс по авторизации, активный блокер, следующий шаг, признак риска после его пересчёта и ссылки на доказательства. Ответ содержит ревизию снимка и сведения об отставании анализа. Digest формирует текст ежедневной сводки.

**Постусловия:** исходные события и сообщения сохранены; группа проанализирована; у задачи актуальный статус, блокер и следующий шаг; прогресс и все изменения доступны в истории с доказательствами. Текст сводки и её доставка остаются ответственностью Digest.

**Ожидаемая запись в сводке после пересчёта риска:** Иван работает над интеграцией API клиента; авторизация готова; продолжение заблокировано ожиданием доступа от клиента; задача длится четыре календарных дня при оценке два дня и отмечена как риск; следующий шаг — проверить интеграцию после получения доступа.

**Отклонения от основного потока:** повторное событие подтверждается без новых изменений; недоступность БД не позволяет подтвердить новую доставку; недоступность LLM оставляет сохранённую группу для отложенного повтора; неоднозначный или невалидный результат не меняет задачу и переходит в предусмотренный повтор либо разбор. Точные правила этих веток приведены ниже.

## 3. Приём, дедупликация и восстановление

### RabbitMQ → inbox

Consumer проверяет поддерживаемый тип и версию, обязательные поля, размер payload, `EventId`, источник и возможность определить команду. В транзакции добавляет `inbox_events`. После commit завершает `Consume`, разрешая подтверждение сообщения транспортом.

- Падение до commit: подтверждения нет, событие доставляется повторно.
- Падение после commit до подтверждения: повтор определяется уникальным ключом inbox.
- Недоступность PostgreSQL: ограниченные транспортные повторы, затем очередь ошибок MassTransit; событие можно переотправить после восстановления.
- Некорректный контракт: терминальная ошибка и очередь ошибок, без бесконечных повторов.

Основной ключ: уникальный `event_id`. Дополнительный ключ транспортной доставки: `(producer, transport_message_id)` при наличии; если идентификатор не глобален для producer, включается тип события. Один транспортный MessageId сам по себе не является глобальным бизнес-ключом.

Нужен и ключ события источника: повторный webhook может породить другой `EventId`. Для Telegram create это `(source_instance, chat_id, message_id, event_type)`, для edit — отдельный идентификатор обновления/ревизии. Для Git — provider instance и стабильный delivery/event ID. Конкретные правила согласуются с Ingestion. Сообщение и редактирование нельзя дедуплицировать только по одному Telegram MessageId.

`ProcessedEventStore` заменяется на inbox. Проверка уникальности обеспечивается ограничениями БД, а не предварительным `SELECT` и локальным семафором.

### Inbox → нормализованные данные

Состояния inbox: `pending`, `processing`, `projected`, `failed`. `projected` означает только завершение нормализации; состояние LLM-анализа хранится отдельно в группе.

Worker атомарно захватывает задания с `locked_until`, `worker_id` и возрастающим `lease_version`. Срок владения продлевается. Завершение разрешено только владельцу актуальной версии; просроченный worker не может записать результат вместо нового владельца. После падения задания возвращаются в обработку по истечении срока владения.

Нормализованные данные и отметка `projected` сохраняются одной транзакцией. Повторный запуск не создаёт второе сообщение или вторую Git-активность.

## 4. Сбор сообщений в группы и контекст

### Ключ накопления

Группа изолирована по команде, источнику, чату и thread/root reply. Если thread отсутствует, используется временное окно чата. Одна группа может включать нескольких сотрудников: реплики коллег нужны для понимания обсуждения. Задачи и сотрудники другой команды в контекст не попадают.

### Стартовые настройки

Это предлагаемые конфигурируемые значения, а не уже измеренные характеристики:

- `IdleWindow = 60 s`: закрыть группу после минуты без новых сообщений.
- `MaxWait = 5 min`: закрыть группу, если старейшее сообщение ждёт пять минут, даже в активном чате.
- `MaxMessages = 100`: ограничить число новых сообщений.
- `MaxInputTokens = 8000`: ограничить весь вход, включая инструкции, схему, новые сообщения и контекст; отдельно резервировать бюджет ответа в пределах окна выбранной модели.
- `MaxContextMessages = 30`, `MaxCandidateTasks = 20`: верхние границы дополнительного контекста.

Любой достигнутый предел закрывает группу. Интервал проверки накопителя — не более 10 секунд. При достижении лимита токенов новые сообщения делятся на несколько групп; одно слишком большое сообщение получает явную политику разбиения/ошибки, не обрезается молча.

Подсчёт токенов выполняется адаптером выбранной модели; до его настройки используется консервативная оценка с запасом. Если даже минимальный запрос не помещается, группа помечается ошибкой размера с сохранёнными исходными сообщениями.

### Неизменяемый состав

Состояния группы: `collecting`, `ready`, `processing`, `retry_wait`, `validated`, `applied`, `needs_review`, `failed`. После закрытия группы её участники и ревизии сообщений неизменяемы. Новые сообщения создают следующую группу. Уникальная связь сообщения/ревизии с основным анализом защищает от включения в две группы. Повторное присутствие старого сообщения как справочного контекста разрешено.

При явном повторном анализе создаётся новая версия анализа с причиной и ссылкой на предыдущую, а не снимается отметка `applied`.

### Что передаём модели

Запрос явно разделяет:

- новые сообщения: внутренний ID, ревизия, автор, время и текст;
- справочные сообщения ветки и связь reply;
- кандидаты задач: ID, исполнитель, статус, блокеры и версия;
- релевантные Git-артефакты, связанные явным ключом;
- разрешённые операции, JSON Schema и правила использования доказательств.

Не включаем всю историю чата. Задачи отбираются по команде, явным ссылкам, участникам и активности. Если кандидатов слишком много, неоднозначность сохраняется, а модель не получает право угадывать отсутствующие идентификаторы. Для MVP достаточно SQL-отбора, явных task keys и reply-связей; семантический поиск можно добавить позже.

При отправке фиксируются снимок входа, версии задач, хеш запроса и версии схемы/промпта/модели. Справочный контекст не становится новым доказательством прогресса за день только из-за повторного включения в запрос.

Нагрузка может задерживать фактическое начало LLM-запроса сверх `MaxWait`: этот параметр ограничивает накопление, а не обещает срок завершения анализа. Возраст готовых групп измеряется отдельно.

## 5. LLM-контракт и применение результата

### Контракт

`IMessageBatchAnalyzer` получает один зафиксированный запрос и возвращает типизированный результат. Конкретный HTTP-клиент и особенности провайдера скрыты за адаптером. Модель и её версия задаются конфигурацией.

JSON Schema версионируется в репозитории вместе с C# DTO. Если провайдер поддерживает принудительное соответствие схеме, адаптер использует эту возможность. Независимо от провайдера результат проверяется локально.

Верхний уровень: `schema_version`, `changes`, `ambiguities`. Для обычного разговора допустимы пустые массивы.

`changes` — типизированные операции: `create_task`, `record_progress`, `set_status`, `set_estimate`, `add_blocker`, `resolve_blocker`, `set_next_step`. Каждая операция содержит `change_ref`, ссылку на задачу, доказательства с ревизиями сообщений и `confidence` от 0 до 1. Для создания задачи используются локальный `new_task_ref`, название и известный сотрудник; настоящий ID генерирует сервис. Последующие операции той же группы могут ссылаться на этот `new_task_ref`.

Существующая задача задаётся `task_id`; новая — `new_task_ref`. Комбинации полей, обязательность, длины строк, перечисления и допустимые числа задаются отдельно для каждого вида операции. Произвольное редактирование любых полей задачи через JSON не разрешается.

Модель не генерирует SQL, не вызывает инструменты и не имеет доступа к БД. Текст переписки трактуется как данные, включая попытки заставить модель изменить формат ответа.

Пример операции для уже известной задачи (ID здесь иллюстративные):

```json
{
  "schema_version": 1,
  "changes": [
    {
      "change_ref": "change-1",
      "action": "add_blocker",
      "task_id": "task-123",
      "description": "Ожидает доступ к production API от клиента",
      "evidence": [
        { "message_id": "message-456", "revision": 1 }
      ],
      "confidence": 0.94
    }
  ],
  "ambiguities": []
}
```

При применении `add_blocker` статус изменяет доменное правило, а не ещё одно свободное поле JSON. Причина блокировки и переход в `blocked` фиксируются вместе.

### Проверки

1. Синтаксис JSON, версия и соответствие схеме; неизвестные поля отклоняются по политике схемы.
2. Сотрудник и задача принадлежат команде и присутствуют в допустимом контексте.
3. Доказательства существуют в зафиксированном входе; изменения требуют хотя бы одно новое сообщение, а не только справочный контекст.
4. Переход состояния, оценка и блокер соответствуют доменным правилам.
5. Версия задачи и ревизии доказательств не изменились с момента формирования запроса.

Низкая уверенность или неразрешённая неоднозначность дают `needs_review` без изменения текущих задач. Начальный порог автообработки — 0.85, с последующей калибровкой на размеченных примерах. Самооценка модели не заменяет проверки и не является гарантией качества.

В MVP группа применяется целиком либо не применяется вообще. Некорректный JSON допускает одну попытку исправления; временные сетевые ошибки/429/5xx — ограниченные повторы с задержкой и jitter. Точное число попыток настраивается; стартовый максимум — пять обращений на версию анализа суммарно, включая исправление формата. После исчерпания попыток группа получает `failed`. Превышение лимита контекста требует разбиения/пересборки, а не повторения идентичного запроса.

### Транзакция применения

LLM вызывается без открытой транзакции БД. Перед применением сервис блокирует строку ревизии команды и повторно проверяет версии затрагиваемых задач/сообщений. Другие компоненты, меняющие задачи, включая Staleness Worker, используют тот же порядок блокировок.

Одним commit сохраняются текущее состояние, изменения, доказательства, прогресс, решение по анализу и `applied` группы. Уникальный ключ `(analysis_id, change_ref)` предотвращает повторное применение. Применённая группа никогда не применяется ещё раз автоматически. Результат анализа сохраняется до применения, чтобы сбой между LLM и commit не требовал повторного вызова модели при наличии валидного сохранённого ответа.

Если контекст задачи устарел, результат не применяется вслепую: группа пересобирает контекст и создаёт следующую версию анализа в пределах лимита попыток. Падение после внешнего ответа, но до его сохранения может привести к повторной оплате LLM-запроса; гарантия здесь — отсутствие двойных изменений БД, а не ровно один внешний вызов.

Порядок событий определяется временем источника и ревизией, а не временем доставки. Старое сообщение может добавить историческое наблюдение, но не откатить текущее состояние автоматически. Противоречие, которое нельзя разрешить по правилам времени/версий, переводит группу в `needs_review`.

## 6. Модель хранения

Все сущности с пользовательскими данными имеют `team_id`, временные поля в UTC и явные внешние ключи. PostgreSQL — единственный источник истины.

- `inbox_events`: event/transport/source IDs, тип и версия, payload JSONB, времена события/приёма, статус нормализации, попытки, lease и ошибка. Хранит повторно обрабатываемый оригинал.
- `employees`, `employee_identities`, `source_bindings`: сотрудники, стабильные внешние идентичности и привязки chat/repository к команде. Username является отображаемым атрибутом. Неизвестная привязка сохраняется для разбора; сотрудник не угадывается по имени.
- `messages`, `message_revisions`: стабильный ключ сообщения, автор, reply/thread, текст, ревизия и время изменения. Ревизии неизменяемы.
- `repository_activities`: repository/provider ID, actor, commit SHA/PR ID, тип и время активности, источник.
- `analysis_batches`, `analysis_batch_items`: ключ накопления, состояние, закрытый состав новых сообщений/ревизий, сроки и lease.
- `analysis_runs`: версия анализа, снимок запроса/контекста, ответ, модель/промпт/схема, токены, длительность, проверки, попытки и ошибка. Ответ LLM не заменяет доменную историю.
- `tasks`: название, исполнитель, текущий статус, оценка, следующий шаг, начало работы, последняя значимая активность, признаки риска, версия строки.
- `task_changes`: типизированное изменение, предыдущие/новые значения, `effective_at` и `recorded_at`, ревизия команды, ссылки на анализ или правило. История append-only.
- `task_evidence`, `task_progress`: ссылки на сообщение/ревизию или Git-артефакт, подтверждённое наблюдение и его время. Позволяют сформировать «прогресс за день», даже если статус задачи не изменился.
- `blockers`: задача, причина, время возникновения/разрешения, доказательства и состояние `open/resolved`.
- `team_revisions`: возрастающая ревизия видимых изменений команды для последовательной выдачи Digest.

`outbox_messages` добавляется, если согласуем публикацию аналитических событий Digest. В варианте с чтением по API обязательной зависимости от outbox нет.

Нужны индексы для ожидающих заданий по состоянию/времени следующей попытки, групп по ключу накопления, сообщений по чату/thread/времени, открытых задач по команде/исполнителю и истории по команде/ревизии. Сроки хранения текста, сырых payload и LLM-запросов настраиваются отдельно от истории задач; исходная настройка согласуется с командой до работы с реальными чатами. TTL не удаляет ещё не обработанные данные.

## 7. Задачи, блокеры, Git и риск

### Состояния

Основные статусы: `in_progress`, `blocked`, `done`. `stale` и `at_risk` — независимые признаки, поскольку задача может быть одновременно заблокированной и просроченной.

- Новая задача требует явного действия и определимого исполнителя.
- `done` выставляется по явному подтверждению завершения, а не по любому положительному сообщению.
- Открытый блокер переводит незавершённую задачу в `blocked`.
- Снятие последнего блокера переводит её в `in_progress`; `done` требует отдельного подтверждения.
- Повторное открытие `done` требует явного нового указания и записи в историю.
- Для завершения задачи с открытыми блокерами результат должен явно разрешать их либо отправляться на разбор; нельзя получить `done` с незаметно оставленным активным блокером.
- «Исправляю авторизацию» и «авторизация завершена» могут относиться к подзадаче: при отсутствии явной связи модель не должна завершать всю интеграцию.

В MVP у задачи один ответственный. Соавторы представлены доказательствами и Git-активностью. Автоматическое объединение похожих задач не выполняется без достаточной явной связи; сомнительные совпадения попадают в `needs_review`.

### Git

Git-активность с явной ссылкой на task key/PR связывается кодом. Несвязанные коммиты сохраняются как активность, но не обновляют произвольную задачу сотрудника. Merge PR не означает автоматическое завершение всей задачи: это разрешается только явным правилом соответствия задачи и PR. Git можно добавить в LLM-контекст обсуждения; отдельный LLM-вызов на каждый commit не нужен.

### Staleness Engine

Работает раз в пять минут даже при отсутствии новых сообщений. Стартовые правила:

- С оценкой: `at_risk`, если `now - started_at > estimate_duration × 1.5`.
- Без оценки: конфигурируемый порог календарного времени, начально три дня; показываем, что это общий порог, а не измеренное среднее команды.
- `stale`: нет значимой активности по задаче два дня.
- У `done` текущие признаки риска снимаются, история сохраняется.

Здесь измеряется календарное время с момента начала, включая ожидание; это не затраченное рабочее время сотрудника. Оценка в днях на MVP явно означает календарную длительность. Рабочие календари и расчёт по медиане сопоставимых задач — следующий этап после накопления данных и согласования правил.

Значимая активность — подтверждённый прогресс, изменение состояния или связанный Git-артефакт, не любое сообщение автора. Повторный запуск правил без изменения результата не создаёт новую запись истории.

## 8. Редактирование, поздние события и разбор

Редактирование создаёт `message_revision`. Незакрытая группа использует актуальную ревизию; закрытая сохраняет прежний снимок и получает связанное задание повторного анализа. Если ревизия изменилась до применения результата, результат считается устаревшим.

Правка уже применённого доказательства не удаляет историю. Для MVP такое изменение переводится в `needs_review` с указанием затронутых задач. Исправление выполняется явной компенсирующей операцией с причиной; автоматического отката всех последующих изменений нет. До разрешения конфликта API возвращает признак disputed evidence у затронутого вывода.

Позднее событие хранит время источника. История различает момент факта и момент, когда Analytics узнал о нём. API возвращает оба времени; Digest может пересчитать старый день по новой ревизии данных.

Для `needs_review` и терминальных ошибок нужен минимальный рабочий механизм: защищённые внутренние endpoints просмотра, повторного запуска и отклонения с причиной. Исправления оформляются доменной командой и журналируются; произвольные SQL-правки не считаются штатным сценарием. Отдельный UI не входит в начальный объём.

## 9. Контракты с Ingestion и Digest

### Что согласовать с Гришей до реализации

- Стабильные Telegram sender ID, source instance, update ID, thread ID при наличии и время сообщения/редактирования из источника. Сейчас их недостаточно в контрактах.
- Отдельное время публикации: текущее `OccurredAt` по умолчанию — время создания объекта, поэтому Ingestion должен явно передавать время исходного факта.
- Стабильные provider/repository/actor/event IDs для Git; сейчас в основном используются имена.
- Привязка событий к команде: на MVP по конфигурации chat/repository; неизвестные источники не смешиваются с известной командой.
- Версионирование контракта: добавление необязательных полей с согласованным поведением для старых событий либо новый контракт для несовместимых изменений. Изменение namespace/типа MassTransit меняет топологию и требует миграции.
- Формирование стабильного `EventId` при повторной публикации и дополнительные source keys.
- Отдельные очереди Analytics и Digest, подготовка подписок до первой публикации, процедура повторной отправки error queue.

Существующие события без новой идентичности принимаются в inbox; нормализация/анализ ждут разрешения привязки либо используют заранее настроенное соответствие. Отсутствующее время источника маркируется как неизвестное, не выдаётся за точное время активности.

### Что согласовать с Артёмом

Предлагаемый API:

- `GET /internal/teams/{teamId}/tasks`: актуальные задачи, фильтры по сотруднику/статусу, блокеры, риск и доказательства.
- `GET /internal/teams/{teamId}/activity?from=...&to=...`: подтверждённый прогресс и изменения за полуоткрытый период `[from, to)`.
- `GET /internal/teams/{teamId}/changes?afterRevision=...`: последовательные изменения по ревизиям, с пагинацией.
- `GET /internal/teams/{teamId}/analysis-health`: возраст ожидающих данных, ошибки/разбор и граница обработанного периода.

Для дневного дайджеста нужен согласованный снимок текущих задач и истории, читаемый в одной транзакции; его можно выдавать отдельным `digest-context` endpoint. Он возвращает `snapshot_revision`, `generated_at`, период/часовой пояс и сведения о ещё не обработанных группах. Пагинация истории ограничивается зафиксированной верхней ревизией, поэтому новые записи не теряются между страницами.

Ревизия команды назначается под блокировкой строки `team_revisions` в транзакции применения. Так курсор не пропускает изменения из транзакций, завершившихся позже. Один только автоинкрементный ID без такого порядка не считается надёжным курсором.

Времена хранятся в UTC. Границы дня рассчитываются по явно настроенному часовому поясу команды. Для истории среза учитываются и время факта, и ревизия записи. Отчёт включает предупреждение о неполноте, если анализ отстаёт или есть неразрешённые группы; пустой список изменений не выдаётся автоматически за отсутствие активности.

API защищён сервисной аутентификацией и проверкой команды. Read API и административные операции имеют разные права. Трассировка использует W3C trace context, если он передан, плюс `CorrelationId`; группа из нескольких событий хранит ссылки на все исходные корреляции, а не перезаписывает их одной.

## 10. LLM-очередь, ограничения и наблюдаемость

Готовые группы являются постоянной внутренней очередью PostgreSQL. `Analysis Worker` ограничивает число запросов в минуту, токены и число параллельных запросов, учитывает timeout и `Retry-After`. При нескольких экземплярах лимит общий для ключа провайдера: до появления распределённого ограничителя активен один LLM dispatcher с lease в БД. Локальный limiter в каждом экземпляре не считается общим лимитом.

Fallback на MVP: повторить позже при недоступности модели; явные Git-правила продолжают работать. Rule-based извлечение очевидных блокеров можно добавить отдельно, с собственным указанием метода и теми же правилами доказательств. Оно не должно создавать видимость успешного LLM-анализа всей группы.

Prometheus:

- `analytics_events_received_total`, `analytics_events_duplicate_total`, `analytics_events_failed_total` по ограниченным типам/источникам;
- `analytics_inbox_pending`, `analytics_batches_ready`, `analytics_batches_oldest_age_seconds`, `analytics_analysis_duration_seconds`;
- `analytics_llm_requests_total`, `analytics_llm_request_duration_seconds`, `analytics_llm_tokens_total`, `analytics_llm_validation_failures_total`;
- `analytics_analysis_needs_review`, `analytics_tasks_at_risk`, `analytics_tasks_stale`.

Event/message/task/employee IDs не используются как labels метрик. Они доступны в JSON-логах и trace attributes. Логи содержат EventId/BatchId/AnalysisId/CorrelationId и причину ошибки, без полного текста сообщений, запросов, ответов и секретов. Сами данные анализа хранятся в БД с контролем доступа.

`/health/live` проверяет процесс. `/health/ready` проверяет БД и готовность приёма RabbitMQ. Временная недоступность LLM отражается как деградация аналитики и рост очереди, а не отключает приём событий. До запуска на реальных данных задаются пороги оповещения по возрасту очереди, ошибкам и отсутствию прогресса.

## 11. Предлагаемая структура кода

Один deployable проект. В начале достаточно папок без дополнительного дробления на библиотеки:

```text
src/AnalyticsService/
  Consumers/                 # RabbitMQ → inbox
  Domain/                    # задачи, блокеры, правила, операции
  Application/
    Projection/              # нормализация событий
    Batching/                # накопление и закрытие групп
    Context/                 # ограниченный снимок контекста
    Analysis/                # интерфейс анализатора, проверки, применение
    Queries/                 # данные задач и дайджеста
  Infrastructure/
    Persistence/             # EF Core/Npgsql, конфигурации, миграции
    Llm/                     # адаптер провайдера, JSON Schema, limiter
    Messaging/               # регистрация MassTransit, inbox/outbox
    Observability/           # метрики, логирование, tracing
  Workers/                   # projector, batcher, analyzer, staleness
  Api/                       # внутренний API и операции разбора
  Options/                   # проверяемая конфигурация
tests/
  AnalyticsService.UnitTests/
  AnalyticsService.IntegrationTests/
  AnalyticsService.Evaluation/ # размеченные диалоги и оценка LLM
```

HTTP API и `/metrics` предполагают web host с `BackgroundService` для workers; остаётся один процесс Analytics. Версии новых пакетов фиксируются после проверки совместимости с текущим .NET и MassTransit 8.5.12.

## 12. План разработки и критерии приёмки этапов

Этапы расположены по зависимостям, без календарных обещаний. Оценку сроков можно дать после согласования контрактов и провайдера LLM.

### Этап 0. Контракты и тестовые сценарии

Результат: согласованные source keys, идентичности, времена, JSON Schema/DTO, формат Digest API и конфигурация команды.

Критерии:

- A01. На каждый поддерживаемый тип есть пример корректного события и правила уникальности; Telegram create/edit различаются.
- A02. По старым контрактам определено поведение при отсутствии новых полей, а несовместимые изменения имеют процедуру миграции.
- A03. Утверждены набор операций LLM, примеры пустого/успешного/неоднозначного ответа и доменные переходы.
- A04. Подготовлены сценарии диалогов: начало, прогресс, завершение, блокер/разрешение, несколько сотрудников, обычный разговор, противоречие, редактирование и поздняя доставка.

### Этап 1. PostgreSQL inbox и приём

Результат: миграции, repository/inbox, consumer с транзакцией, удаление зависимости от локального ProcessedEventStore.

Критерии:

- A05. Сотня доставок одного события создаёт одну строку inbox, в том числе при двух экземплярах и перезапусках.
- A06. Повтор webhook с новым EventId и тем же source key не создаёт второй нормализованный факт; edit создаёт отдельную ревизию.
- A07. Сбои до/после commit и до подтверждения не теряют событие; повтор безопасен.
- A08. Некорректный payload и недоступная БД дают предусмотренные error/retry сценарии; ручная переотправка после восстановления успешна.

### Этап 2. Проекция и накопление групп

Результат: нормализованные сообщения/идентичности/Git-активность, lease workers и Batch Builder.

Критерии:

- A09. Двадцать сообщений одной ветки за 30 секунд дают одну группу; при успешном ответе выполняется один LLM-вызов. Сообщения разных команд не смешиваются.
- A10. Проверки с управляемыми часами подтверждают закрытие по тишине, MaxWait, числу сообщений и бюджету токенов с точностью интервала проверки; непрерывный поток не блокирует закрытие.
- A11. Новое сообщение после закрытия идёт в следующую группу; каждое новое сообщение имеет ровно одно основное назначение группе.
- A12. Два workers не применяют одну работу одновременно; после истечения lease работу забирает новый владелец, а старый не может завершить её своей версией.
- A13. После перезапуска не теряются накопленные сообщения, закрытые группы и ожидающие повторы. Неизвестная идентичность не создаёт ложного сотрудника.

### Этап 3. Задачи и история с тестовым анализатором

Результат: доменная модель, изменения, блокеры, доказательства и атомарное применение. Сначала используется детерминированный fake-анализатор, без зависимости от реального LLM.

Критерии:

- A14. На сценарии «начал → прогресс → блокер → снят блокер → завершил» состояние и вся история корректны; прогресс виден отдельно от статуса.
- A15. Повтор применения одного analysis_id не создаёт повторных задач, блокеров, прогресса или истории.
- A16. Сбой в середине транзакции не оставляет частичных изменений. После повторного запуска применяется один полный результат.
- A17. Позднее сообщение не откатывает новый статус автоматически; конкурентное изменение версии вызывает пересборку контекста или разбор.
- A18. Изменение доказательства после применения помечает спорный вывод и создаёт разбор; исходная история не удаляется.

### Этап 4. LLM по строгой схеме

Результат: адаптер, промпт, JSON Schema/DTO, ограничитель, сохранение анализа и обработка ошибок.

Критерии:

- A19. Невалидный JSON, неизвестный ID, отсутствующее доказательство, ссылка на другую команду и запрещённый переход не изменяют задачи.
- A20. Обычный разговор с `changes: []` успешно завершается без задач; неоднозначный результат попадает в разбор.
- A21. Timeout, 429 и 5xx приводят к отложенным ограниченным повторам; успешно сохранённый ответ используется после перезапуска без нового вызова модели, если контекст актуален.
- A22. При двух экземплярах суммарные обращения не превышают настроенные лимиты; временная недоступность LLM не останавливает сохранение новых событий.
- A23. Запросы не превышают выбранное окно модели с резервом ответа; инструкция внутри сообщения не даёт обходить схему, разрешённые ссылки и доменные проверки.

### Этап 5. Git и Staleness Engine

Результат: явные связи артефактов с задачами, прогресс и независимый пересчёт риска.

Критерии:

- A24. Связанный commit/PR добавляет доказательство и активность; несвязанный не меняет чужую задачу. Merge без правила не завершает задачу.
- A25. Управляемые часы подтверждают пороги оценки, отсутствие оценки и stale. При отсутствии событий worker всё равно обновляет риски.
- A26. Повторный пересчёт не дублирует историю; done снимает текущие флаги, сохраняя прошлые значения. API явно различает календарную длительность и оценку.

### Этап 6. Digest API, разбор и наблюдаемость

Результат: внутренний HTTP API, курсоры/снимки, защищённые операции разбора, метрики, traces и runbook.

Критерии:

- A27. Дневной срез по часовому поясу содержит актуальные задачи, прогресс, новые/разрешённые блокеры, риски и источники; границы периода `[from, to)` проверены.
- A28. При конкурентных commit и пагинации курсор не пропускает изменения; повтор чтения того же снимка даёт согласованный результат.
- A29. Позднее событие видно как новая ревизия с исходным effective_at; отставание анализа и спорные выводы отражены в API.
- A30. Запрос другой команды и административный запрос без нужных прав отклоняются. Повтор/отклонение/исправление разбора оставляют аудит.
- A31. `/metrics`, live/ready и цепочка EventId → BatchId → AnalysisId → TaskChange доступны; тексты и секреты отсутствуют в логах, ID отсутствуют в labels метрик.

### Этап 7. Сквозная проверка и качество

Результат: проверяемая сборка MVP, оценка извлечения на размеченных диалогах и эксплуатационные инструкции.

Критерии:

- A32. Автотест с настоящими PostgreSQL и RabbitMQ проводит события от публикации до Digest API, включая повторную доставку и перезапуск worker.
- A33. На предложенном стартовом профиле 5 событий/с в течение 10 минут, без ограничения со стороны брокера/БД, p95 приёма в inbox ≤ 1 секунды, потерь/дублей применения нет. При перегрузке LLM очередь сохраняется и обрабатывается после восстановления. Это цель приёмки, не измеренный результат текущего кода.
- A34. На отдельном размеченном наборе не менее 100 групп предлагаемые пороги: precision автоматически применённых изменений ≥ 0.90; recall автоматически выявленных блокеров ≥ 0.80; доля групп с ложной новой задачей на обычном разговоре ≤ 0.05; доля однозначных групп с ожидаемыми изменениями, обработанных автоматически, ≥ 0.70. Отдельно считаются доля needs_review и ошибки определения исполнителя/задачи. Набор содержит все сценарии A04; соответствие изменений эталону проверяет человек по заранее принятой разметке. Пороги фиксируются до оценки, confidence модели не используется как эталон, тестовый набор не используется для подбора промпта.
- A35. Проверены восстановление из backup PostgreSQL в тестовом окружении, повтор error queue, обработка зависших leases, лимиты LLM и безопасный повтор разбора; есть инструкция запуска и миграций.

### Граница готовности MVP

MVP считается готовым после этапов 0–7: события надёжно приняты, сообщения анализируются группами по строгому контракту, задачи и история подтверждены источниками, риски обновляются без новых событий, Digest получает согласованный срез с признаками неполноты, а основные сбои воспроизводимо пройдены.

Redis, векторный поиск, автоматическое слияние задач, несколько исполнителей одной задачи, рабочие календари, статистические нормы по типам задач, автоматические компенсации после редактирования и полноценный UI разбора остаются последующими улучшениями.

## 13. Ближайший шаг

Начать с этапов 0–1: согласовать недостающие поля с Ingestion, зафиксировать схемы, добавить PostgreSQL и миграцию inbox. Параллельные вызовы LLM и расширение текущего in-memory семафора не решают задачу надёжного хранения и поэтому не являются первым этапом.
